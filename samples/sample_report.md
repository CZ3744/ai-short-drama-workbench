# 脚本驱动的 AI 视频自动生产系统

当我们谈论 AI 视频生成时，很多人第一反应是“输入一句提示词，然后等待模型吐出一段炫酷视频”。这个想象很诱人，但对于真正的内容生产来说，它只解决了很小的一部分问题。一个可用的视频不是单个镜头，而是一条连续的叙事链：它需要清楚的主题、稳定的结构、合适的语气、节奏合理的分镜、可读的字幕、能解释复杂概念的画面，以及最终可以复盘、修改、重新导出的工程记录。

脚本驱动的思路，是把“初始稿”当成视频生产的唯一源头。用户只需要粘贴一篇文章、报告或课程讲义，系统首先理解它的主题、受众和核心观点，再判断它更像 B 站知识讲解、报告解读、课程切片，还是产品说明。这个阶段不急着生成画面，而是先把内容变成结构化的理解结果：这篇稿子到底想说明什么，哪些段落需要保留原文，哪些地方需要拆开，哪些抽象概念需要图解，哪里应该插入章节标题页，哪里需要放慢节奏。

接下来，Scene Planner 会把长文本切成一个个 scene。一个 scene 不应该承载太多意思，它最好只回答一个问题、呈现一个观点，时长控制在十几秒左右。对于长段落，系统会继续拆分；对于章节切换，系统会插入标题卡；对于密集概念，系统会倾向使用结构图或关键词卡片。这样做的价值不是让机器替代创作者，而是让创作者不用在混乱的时间线上反复猜测：“这一段到底该放什么画面？”

Visual Director 的职责，是把每个 scene 变成可执行的视觉目标。即使今晚没有接入真实生图和生视频模型，系统也不能随便生成黑底白字的临时图。它应该明确每一段画面的目的：是建立主题、解释流程、突出关键词，还是展示一个未来可以交给视频 provider 的镜头。当前版本会使用程序化卡片、柔和背景、玻璃质感面板、关键词标签和简单流程图来完成本地 fallback。画面不一定惊艳，但必须清楚、克制、可读，并且为未来替换高质量模型留下 prompt 和 provider 插槽。

音频也是同样的策略。没有真实 TTS 时，系统不应该中断，而是生成静音音轨，保证 final.mp4 可以完整合成。字幕由 narration_text 自动切分成 SRT，时长根据 scene 估算分配。这样，用户至少可以拿到一个结构正确、节奏可检查、文件完整的视频草案。等后续接入 edge-tts、Piper、Azure、ElevenLabs 或其他中文 TTS provider，音频模块可以被替换，而不用推倒整个工作流。

真正让这个系统接近产品雏形的，是它的可追踪性。每个 job 都有独立输出目录：输入稿、scene_manifest、素材、音频、字幕、渲染文件、日志和 QA 报告都会被保存。LLM 的每一次调用都会记录 agent 名称、prompt 文件、输入摘要、输出摘要和错误信息，但不会记录 API Key。这样，当某个 scene 切得不好、某个 visual prompt 太空、某个字幕太长，用户不是只能重新来过，而是可以知道问题发生在哪一步。

修改意见流程则让系统从“线性脚本”变成“可迭代工作台”。用户可以说：“第 3 段画面太普通，改成系统架构图风格。”系统会调用 Revision Agent 判断影响范围：是只改 visual_prompt，还是需要重做字幕，还是需要全片重新切片。如果只是局部问题，系统会尽量局部更新 manifest，再重新生成相关素材并渲染；如果是整体节奏或语气问题，系统才会走全片重规划。这个判断能力，是 LLM 真正适合参与创作流程的地方。

最后，QA Agent 会检查 manifest 和输出文件。它会看 scene 是否太长，screen_text 是否拥挤，visual_prompt 是否具体，字幕是否存在，final.mp4 是否可播放，分辨率和音频轨是否符合预期。工程检查负责文件和编码，LLM 检查负责内容质量和分镜合理性。两者结合，才能避免“看起来跑完了，其实没法交付”的假成功。

所以，这个系统的定位不是一次性生成大片，而是搭建一条可以逐步增强的生产线。今晚的版本用本地工具和 fallback 打通闭环；明天可以接入真实 TTS；之后可以接入图像模型、视频模型、素材库、局部重渲染、B 站发布辅助。只要底层结构足够清晰，能力就可以一层一层替换上去。脚本是起点，manifest 是骨架，provider 是可替换肌肉，而最终的视频只是这个工作流自然流出的结果。
